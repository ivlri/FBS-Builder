## 1. Цель системы

Построить **production-ready систему раскладки блоков**, которая:

* работает с **произвольной конфигурацией стен** (разная длина, разная высота)
* **не переобучается** под каждый проект — одна обученная policy применяется ко всем проектам
* использует RL **только для локальной оптимизации**, а не для глобального планирования

---

## 2. Ключевой принцип
Агент:

* не знает про проект
* не знает про порядок стен
* не знает про соседние стены

Она знает только:

> "Как выбрать и поставить блок в текущей стене при данных ограничениях"

### Обучение vs Inference

* **Обучение** — один раз, на рандомизированных стенах (разные длины, разные blocked-зоны). Результат — файл весов (`ppo_fbs_builder.zip`). Это этап подбора параметров нейросети.
* **Inference (прод)** — policy получает observation (стену + ограничения), выдаёт action (блок + позиция). Один прогон, без дообучения. Агент **не учится заново** на каждую стену.

Если policy обучена на достаточно разнообразных конфигурациях, она **генерализует** на новые стены без дообучения.

## 3. Архитектура: три компонента

```
┌─────────────────────────────────────────────────┐
│                   PIPELINE                      │
│                                                 │
│  ┌──────────┐    ┌────────────────┐    ┌──────┐ │
│  │ Planner  │───>│ Context Builder│───>│  RL  │ │
│  │ (алгор.) │    │   (алгоритм)   │    │Agent │ │
│  └──────────┘    └────────────────┘    └──────┘ │
│       │                                   │     │
│       │          результат раскладки      │     │
│       │<──────────────────────────────────┘     │
│       │                                         │
│       │  (передаёт результат в Context Builder  │
│       │   для следующей стены)                  │
│       v                                         │
│   Следующая стена                               │
└─────────────────────────────────────────────────┘
```

Цикл в проде:
```python
for wall in planned_order:
    context = context_builder(wall, built_neighbors)
    result = rl_policy.predict(context)   # inference, не обучение
    save_result(wall, result)
```

## 4. Зоны ответственности

### 4.1 Planner (жадный алгоритм)

Решает **глобальные и конструктивные вопросы**:

* порядок обработки стен (обход графа)
* граф примыканий (какие стены соседние)
* углы и Т-образные стыки
* правила заводки блоков в соседние стены
* шахматный порядок по высоте как конструктивное правило

**Важно:**:
* порядок обхода стен влияет на ограничения для последующих стен
* при 10+ стенах может понадобиться жадная эвристика для выбора порядка (например: начинать с самой длинной стены, или с угловой, или по BFS от входа)
---

### 4.2 Context Builder (алгоритм)

Переводит результаты Planner и предыдущих раскладок в **локальные ограничения** для одной стены.

Формирует:

* `context_grid` — матрица (layers, cells), где заблокированные зоны содержат **тип блока**, а не просто 0/1. Это критично: шов от заведённого блока влияет на правила перевязки внутри текущей стены. Бинарная маска теряет эту информацию.
* `blocked_mask` — бинарная маска, производная от context_grid (где нельзя ставить)
* `support_mask` — допустимая опора снизу
* `offset_constraints` — смещения швов от соседних стен
* `current_layer` — текущий слой
* `wall_role` — START / MIDDLE / END (опционально)

Контекст **статичен внутри одного эпизода** (стены).

**Шахматный порядок** при заводке блоков в соседнюю стену — это **hard constraint**, а не поведение, которое агент должен "выучить". Context Builder формирует ограничения так, чтобы шахматный порядок был **невозможно нарушить** (через action mask).

---

### 4.3 RL FBS Builder (один агент, одна policy)

RL:

* видит **только текущую стену** и её ограничения
* **не знает причин** ограничений (пришли от соседней стены, от коммуникаций, или от угла — для агента это одно и то же)

RL решает:

* какой блок выбрать
* куда его поставить

RL **не решает**:

* порядок стен
* правила перевязки между стенами (получает от Context Builder глобальные ограничения в action mask)
* логику проекта

## 5. Обработка стен переменной длины

Стены могут быть разной длины. Решение — **padding + masking**:

* Определить `MAX_CELLS` — максимальная длина стены в проекте (в ячейках по 20мм)
* Все стены дополняются до `MAX_CELLS` нулями справа
* Позиции за пределами реальной стены маскируются в `action_mask` — агент не может туда ставить блоки
* Observation space фиксированного размера: `grid: (max_layers, MAX_CELLS)`

Это стандартный подход (padding + attention mask), хорошо работает с нейросетями.

---

## 6. Randomization при обучении

Для генерализации **обязательна** рандомизация при обучении:

* Каждый эпизод — **случайная длина стены** (в пределах допустимого диапазона)
* Каждый эпизод — **случайные blocked-зоны** (имитация соседних стен, проёмов, коммуникаций)
* Вариация размеров и позиций заблокированных зон
* Вариация `wall_role` (START / MIDDLE / END)

Без рандомизации модель запомнит одну конфигурацию и не сможет работать с новой.

## 8. Открытые вопросы

### 8.1 Оценка качества порядка обхода стен
Как Planner определяет, что его порядок хороший? Нужна метрика (например: суммарная площадь заблокированных зон, или итоговый процент крупных блоков).

### 8.2 Context Builder: глубина контекста
Достаточно ли передавать только blocked-зоны от непосредственных соседей? Или нужно учитывать соседей второго порядка? На практике, скорее всего, достаточно первого порядка.

### 8.3 Масштаб MAX_CELLS
При большом MAX_CELLS action space растёт (n_types * MAX_CELLS).

**Текущая конфигурация:**
- MAX_CELLS = 300 (6000mm / 20mm)
- n_types = 11
- Action space = 11 × 300 + 1 = **3301 actions**

**Если стены до 12м:**
- MAX_CELLS = 600
- Action space = 11 × 600 + 1 = **6601 actions**
- Это предел для MaskablePPO — нужно следить за временем обучения

### 8.4 Многоэтажность
Если высота стен тоже варьируется, нужен аналогичный padding по высоте (MAX_LAYERS).
